# PostgreSQL 17 provider compatibility qualification

**Test plan, not a completed provider certification.** No provider account, database or billable resource has been created by this work. Execute only after owner authorization on a disposable synthetic database, never against production or shared student data. Linked work: [5A backlog](MILESTONE_5A_IMPLEMENTATION_BACKLOG.md), [gate register](LAUNCH_READINESS_GATES.md), existing `docs/DATABASE_SECURITY.md` and `docs/AUTHENTICATION.md`.

Candidates remain a private self-managed PG17 VM, managed PostgreSQL with private Django hosting, or an approved managed app + PG17 combination. Brand/version marketing and cheap prices are insufficient. Record one result per **provider + SKU + region + endpoint/pool mode + release SHA**; a passing local Docker PostgreSQL 17 test is not a passing managed-service result. Do not relax a role guard, extension-placement check, FORCE RLS or TLS validation to make a provider pass.

## Entry conditions and evidence format

Owner approves the spend ceiling (including restore clones/storage/egress), deletion/shutdown date, region/terms, test window and rate bounds. Use separate test-only secrets delivered through the secret store/environment, not command-line URLs, screenshots or committed `.env`. Disable outbound real mail and put a maintenance/private gate in front of any restored application. Verify targets and disposable DB names before destructive operations. Retain sanitized metadata and assertions, never rows, password hashes, tokens, dumps, connection strings or private signing keys in GitHub/CI logs.

For each case retain: case ID, exact script/test revision, UTC time, operator/reviewer, build/settings revision, database `server_version_num`, actual role names/flags, sanitized assertions, pass/fail/not-run, reason, artifact digest and teardown outcome. Secrets have version references only. Record actual SQLSTATE on permission/constraint failures, without SQL bind values. Evidence must identify use of direct connections versus pooled endpoints and SCRAM versus provider authentication.

## Suggested command boundaries

Run the repository's existing commands through an offline test migrator, with current pinned dependencies. The test runners provision actual auth/runtime logins; never substitute SQLite, the vendor admin URL as web credentials, or a fake-role-only run. Test database creation may require a dedicated test migrator with CREATEDB, unlike an ordinary deployed migration job. If provider restricts database/role creation, obtain an approved isolated test-cluster/provisioning arrangement; do not silently replace the project's runner or weaken its assertions.

```sh
python server/manage.py check
python server/manage.py makemigrations --check --dry-run
python server/manage.py test accounts academics --settings=config.settings.test -v 2
python server/manage.py test security_tests --settings=config.settings.security_test -v 2
python server/manage.py test auth_tests --settings=config.settings.auth_test -v 2
python server/manage.py test web_tests --settings=config.settings.web_test -v 2
```

These are distinct runs with separate disposable test DB names and the correct foundation-vs-restricted-role provisioning from the repository docs/CI. They are not a copy/paste deployment script: supply the right test credentials/profile for each, and verify absence of real data first. A fresh migration, upgrade from the accepted previous schema and documented reversal/forward-recovery drill are all needed. Drift checks should reject skipped migrations or stale grants.

Safe catalog assertions include `current_user`, `session_user`, `rolsuper/rolbypassrls/rolinherit`, `pg_auth_members`, `pg_class.relrowsecurity/relforcerowsecurity`, `pg_extension.extnamespace`, verifier `prosecdef/proconfig`, `has_table_privilege` (including MAINTAIN) and exact effective column UPDATE sets. Do not dump context_key rows or connection DSNs as evidence. For TLS inspect negotiated protocol/cipher and certificate metadata, not passwords. A test report should record whether database encryption at rest and backup encryption are provider claims, contractual controls or independently exercised behavior.

## Restoration and auth-state safety sequence

1. Put the new environment behind a deny-all/maintenance gate; block mail and background external effects. Confirm destination differs from source. Time recovery from incident declaration, not just pg_restore duration.
2. Recover encryption keys via the approved independent path and restore the consistent dump/snapshot with a recorded artifact/source recovery point. Do not let arbitrary role owners or privileged URLs enter web settings.
3. Reconcile exact ownership and grants using the accepted migrations/provisioning; run guards as real app logins. Restore of schema objects must not turn app roles into owners. Provision a fresh signed-context key in both database and app and prove old contexts fail.
4. Execute a separately reviewed invalidation procedure: purge restored Django sessions, invalidate all outstanding restored email proofs, delete trusted-device evidence and change relevant cookie/key versions or epochs as required. Preserve/reinitialize generation barriers explicitly so no pre-restore in-flight issuance can become current. Coordinate shutting down old workers/pools; changing a counter without fencing old workers is insufficient.
5. Define throttle-state handling explicitly: restoring an old counter snapshot can reopen guessing allowances; resetting buckets or rotating their HMAC key is not automatically safe. Keep admission gated until approved protection state/operational limits are established. Do not disable account isolation to get a restore smoke test to pass.
6. Verify two-student access, direct-SQL denial, valid fresh login and invalid old session/link/cookie/context, all academic constraints and known synthetic calculations. Restore off-site access/alerts only after checks pass. Retain the sanitized report and approved disposition, then delete the disposable target/backup according to policy.

A provider-native PITR drill must prove the requested timestamp, documented recovery window and role/extension/TLS behavior on the resulting endpoint. A “backup enabled” screenshot, VM image or successful pg_dump exit alone is not a restoration test. Provisional daily backup/RPO ≤24 h/RTO ≤4 h and seven daily/four weekly copies are proposals requiring owner approval; no achievement is claimed.

## Qualification decision

Choose **pass**, **reject configuration**, or **blocked/not tested** per case. Mandatory cases cannot be waived by a cheap price, a successful SQL connection, or localhost success. Escalate incompatibilities for a written architecture decision before procurement; retain the forced-RLS/role boundary. Record permission/cost/region/retention/provider-admin-access caveats and obtain final operator + independent reviewer sign-off. No provider is currently certified by this plan.
