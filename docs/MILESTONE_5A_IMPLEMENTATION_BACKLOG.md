## Intended outcome and scope

Deliver a repeatable **private, synthetic-data staging lab** with tested security boundaries, operational recovery and product-quality evidence. It is not a public pilot. CLI/Streamlit remain independent local applications; personal JSON, academic formulas and Claude's authentication implementation remain untouched. Do not implement this backlog merely because its planning PR is merged.

A minimal future topology is a private-access TLS proxy → loopback WSGI → PostgreSQL 17 via restricted academic runtime and auth logins. Offline migration/backup jobs use separate credentials absent from web processes. A small self-managed VM is provisional only: managed hosting is preferable if no one can own patching/restoration. Every managed provider must first pass the compatibility plan without weakening role/RLS checks.

## What can be developed and tested without buying services

On existing hardware and after a separate implementation authorization, 5A-03–13 and 15–20 can produce substantial local evidence: WSGI/static service packaging, a local TLS proxy and CA, generated SCRAM roles, migrations/rollback, exact privilege checks, forced RLS/signed context, private SMTP sink, failure injection, encrypted backup and fresh restore, sanitized alert sinks, local browser/mobile-size tests and bounded load tests. CI integration and dependency/safety checks require no new purchased service under current access, although existing CI/compute quotas still apply.

Local TLS/SMTP/VPN simulation proves application behavior only. It cannot establish a vendor's private origin controls, actual PG17 SKU/privileges/pgcrypto policy, certificate chain, provider backup/PITR, regional performance, mailbox arrival, DNS reputation, retention/deletion or terms. Real phones/screen readers and people may be available without purchase, but record unavailable combinations as untested. A free vendor trial is still an external account/data-processing decision and is not implicitly authorized.

## Recommended sequence and security integration boundary

1. Approve the local work scope/package choices and owners; settle release ledger and data policy. Begin local harness and provider-neutral evidence templates without waiting for a hosting purchase.
2. Build the local settings/artifact/role/RLS/proxy/TLS foundation, then backups/restoration/release rehearsal. Complete observability and SMTP-sink work alongside it.
3. Re-verify the integrated security release, historical compatibility, browser/accessibility and bounded performance. PR #29 remains unmerged; its approval does not make master safe against its baseline reset/hash-upgrade race. PR #26 is dormant schema/primitives only and does not enable account-aware throttling/recovery.
4. Obtain owner decisions and current quote, then run provider compatibility **before** treating a candidate as selected. Prefer direct connections initially; review pooling separately.
5. Only after further authorization provision the private lab; verify actual email and off-site restore/alerts. Invite controlled synthetic reviewers only after gates pass.
6. Prepare independent penetration testing and retests; return to owner for a separate launch decision. No public exposure or account enforcement is authorized by this plan.

Unresolved S0-02B/C protection/recovery work does not block provider-neutral local packaging or database experiments. It **does** block claiming enforced account throttling/recovery is ready, enabling unfamiliar-browser hard gates, or accepting a public launch based on 02A alone. Do not repair authentication as part of staging implementation; give findings to Claude through the authorized review workflow.
